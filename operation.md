# DDCS V4.1 — operation

> Every measured statement names the bench test that measured it (see evidence.md).

## Measured on this controller

- Big files load and run: 20 000 lines (180 KB) started at once and 100 000 lines (900 KB) about 6 s later. Tiny segments are limited by the BLOCK RATE, which follows Pr124 "interpolation period": in a straight line, 6 000 segments of 0.1 mm at F3000 (ideal 12 s) ran at about 175-180 blocks per second, about 1060 mm/min (35 % of F), at the factory Pr124 = 0.005; with Pr124 = 0.002 (loaded by a reboot) about 350 blocks per second, about 2100 mm/min (70 % of F). Comments on every line and long lines did not change it. A zig-zag (each 0.1 mm segment reversing direction) ran at about 34 reversals per second, about 29 ms each, and neither Pr104 (acceleration 2000) nor Pr124 changed that: its cause is not known. Pr124 took effect only after a reboot; Pr104 and Pr109 written from a program changed nothing (4 straight runs, 1 run of each other case). *(the CAM-file test, 2026-10-30 + the throughput test, 2026-10-31 (every setting restored, the setting file byte-compared))*
- M3 waits Pr194, the spindle start-up time, before the next line: with #694 = 10 written in the program the run took about 8-10 s longer than the control, so the write applies at once. Pause in the middle of a G1, then Start, RESUMES the move: a G91 X300 from X30 ended at exactly X330 (1 run each). *(the operation test, 2026-10-31)*
- A soft limit enabled from a program (Pr234 = 1, written as #734) takes effect at once. G0 X800 (beyond the limit) stopped exactly on the limit, machine X 860.000, and the program ENDED there silently: READY, no message, and the lines after it never ran (1 run; #734 restored to 0). *(the probe / soft-limit test, 2026-10-31)*
- M6 in a program does NOTHING while Pr905 "Tool change command M6 back to reference point 1 pause" is No (the factory value): no pause, no dialog, no move, and the current tool is not set; the program runs on. With Pr905 = Yes, M6 runs the vendor tool change (O10006 in slib-m.nc), whose first move is G53 to the tool-change point, so an unhomed machine stops there ("HOME operation not performed"). *(the M6 test, 2026-10-30 (Pr905 No, then Yes; restored and byte-compared))*
- #1806-#1809 are per-axis (X Y Z A) "search the switch on G28" switches, and WRITE-ONLY: every read returns the same garbage (about 5.2e180), at boot or after any write. With #1806 = 1 (what the vendor home files write) G91 G28 X0 searches for the switch; with #1806 = 0 it homes X INSTANTLY, with no search and no motion: machine X is SET to its reference point (Pr800, #1300) where the axis stands, and the axis shows as homed. A 0 written in one program still holds in the next (1 run each). *(the home-flag test, 2026-10-31)*
- The vendor M6 (Pr905 = Yes, the machine homed): T1 M6 parks with G53 at #1300-#1302, then opens M6.rc ("Please change tool: No.1", then "After changing the tool, select next action"). Its choice is #148: 0 "Call current length compensation" or 1 "Perform tool length measurement"; its fields are #106 feed, #102 safe Z, #103 / #104 the setter X Y, #105 the measuring Z. With 0 the current tool is set (#1824 = 1) and G43 H1 applies the stored length. With 1 it moves to the setter, probes with G31 L#682, writes the new length to #764 as #1502 - #108 (#108 is the setter reference), sets #1560 = 1 (wear mode) and zeroes the wear (#1561), then G43 H1 applies the new length. The dialog shows its fields with 4 decimals and Ok WRITES them back rounded (#104 26.56505117707799 came back as 26.5651) (1 run each). *(the M6 test, 2026-10-31 (homed with the flags at 0; restored and byte-compared))*
- The tool table survives a reboot through #764+: the boot loads #1561+ from #764+, with the tool number minus 1 as the index (#764 for tool 1, #765 for tool 2). With #764 = 2 and #765 = 3 written, then a soft reboot, #1561 = 2 and #1562 = 3, #764 / #765 still held 2 / 3, and G43 H1 / H2 applied them (work Z 20 became 18 / 17; G49 back to 20). A write to #1561 alone takes effect at once but is replaced at the next boot (1 run). *(the tool-table test (Program C), 2026-11-01 (restored, the setting file byte-equal))*
- MULTI-PART: the V4.1 has a built-in "Sequence machining" that runs the SAME program once at each of a list of positions (Array is the regular-grid version, set on the panel), fed by sysdisk/template.txt: one line per part, seven space-separated numbers, Origin-X Origin-Y Origin-Z Origin-A Rotate-angle R-Center-X R-Center-Y (a two-line file 10 20 0 0 0 0 0 and 60 20 0 0 90 60 20 filled the table exactly). CRLF is accepted. The page reads a converted copy named "template" on the system disk, and that copy persists: after template.txt was deleted the page still showed the old rows. *(template.txt on the bench (Sequence machining page) and AUDIT_MENU_TEMPLATE_RC)*
- REAL SEQUENCE MACHINING, measured with a real panel-menu run of a 3-row template. Start it on the panel with Shift, then the DOWN arrow to Advanced Machining, ENTER, DOWN to Sequence Machining, ENTER: arrows, not the numbers 5 and 2 of the manual (there is a submenu and no item numbers). The page lists the template.txt rows (seven numbers per row, see v41-flow-template-txt); its Ok is an Enter hold of about 2 s (a USB device that really holds takes it, a tap does not), and no Advanced Startup dialog followed when the specified line was valid. Each part runs the selected program once with its row origin ADDED to the active work coordinate (a G52 offset: mach X 91.78, 101.78, 111.78 for G54 X 81.78 and the rows 10, 20, 30, work X reading 0 at each part start); #496 is the 0-based part counter (0, 1, 2) and #499 is 1. The program file is RE-READ before EACH part: a file replaced by a rename during part 1 ran from part 2 on, and part 1 kept its own copy. There is no wait and no prompt between parts (about 2-5 s of driver overhead between one M30 and the next part first variable write); the run stops by itself after the last template row, and no post-end fast pass followed (v41-var-after-run-reread is about an ordinary run). WHAT IT IS FOR: the same program at several positions. To run DIFFERENT code per step, or to feed new values into a run, do not swap the file under Sequence machining: use one program with an M47 loop (v41-recipe-feed-running-program), which needs no panel menu and has no race. If a file IS swapped per part anyway, it must have part n+1 on disk before part n ends, because the next part starts 2-5 s after M30 with no wait; writing it right after part n STARTS is safe, the running part keeps its copy. Not covered: the template Z column and rotation (all 0 here), a long wait in the body, more than 4 rows; an M0 or a pause in the body, a part with no motion and the stop actions are measured: v41-hazard-seq-pause-reruns, v41-hazard-seq-motionless, v41-seq-stop-actions. *(AUDIT_SEQ_REAL, a real panel-menu run, one run; t3940)*
- ⛔ A Sequence machining part with NO motion in it resets the run: about 5 s after the page Ok the status went RESET with no message and no line of the part ran (2 of 2; the page showed the X, Y and Z range as [100000,-100000]). The same part with a 0.1 mm move and back added ran all its parts (1 of 1). A part that only writes variables or dwells needs at least one move to run under Sequence machining. *(a bench script (R1-R2c, S1-S5, S4a/b), real panel-menu Sequence runs, 2026-10-29)*
- ⛔ Inside a Sequence machining part, Start after a pause RE-RUNS the part from its first line; it never resumes. After an M0, every Start re-ran the part from the top (8 of 8), the code after the M0 never ran and the sequence never reached the next part, so an M0 for a tool change makes the sequence loop on that part. After the Pause key and Start, the part also ran from the top again, then the next parts ran (1 run). On a real machine everything before the pause is cut again. Do not put an M0 in a program run by Sequence machining. *(a bench script (R1-R2c, S1-S5, S4a/b), real panel-menu Sequence runs, 2026-10-29)*
- At a stop inside a Sequence machining part (an M0 reached by a guard, the file on disk replaced at the stop; 1 run each): Start re-runs the CURRENT part from the top with the file now on disk, then the sequence continues; Reset then Start ends the sequence (the Start is ignored in RESET); Reset twice then Start runs the file on disk once as a plain program and the sequence does not continue. So the one clean fix at such a stop is to put the right file in place and press Start (that part is redone). The template is read once at the start: a row added to template.txt during a run did not run (1 run). M2 ends a part the same way M30 does (1 run). No way to restart a sequence at part N was found: after a Reset during part 2 the menu Advanced Startup is the single-workpiece dialog (no part field), and the page row highlight did not set the start part (row 3 highlighted, the run started at part 1, 2 runs; row 2 untested). The Pause key lifts Z 5 mm and Start puts it back; a paused part reads CONT and READY like an idle controller. *(a bench script (R1-R2c, S1-S5, S4a/b), real panel-menu Sequence runs, 2026-10-29)*
