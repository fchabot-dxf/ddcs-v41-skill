# DDCS V4.1 — operator prompts and dialogs

> Every measured statement names the bench test that measured it (see evidence.md).


## The .rc dialog

A prompt, a number entry and a 2-way choice are each a `.rc` dialog file the program opens with `MarcoDialog "<full path>"`. The operator HOLDS Ok to continue; Cancel ends the program.

The dialog's own last line, which tells the operator how to continue: "Hold Ok to continue".

If a prompt's text cannot be drawn in a dialog, it falls back to `( text )` + `M0` with "Press Start to continue".

A choice is a RADIO of exactly 2 labels writing the chosen 0-based index into #192; the program branches on it right after the dialog.

A number entry is an EDIT bound to the target variable, decimal, -10000..10000, 10 characters wide.

## Where the dialog file lives

The program calls each dialog by FULL path, in the folder it runs from:

- Work disk: `/local/`
- USB stick: `/udisk-sda1/`

- **One dialog**: the program CARRIES it — the dialog's lines at the top, each prefixed with `;`, and `MarcoDialog "<folder>/<program>.nc"` (the program opens itself). Renaming or moving the file breaks its dialog.
- **Two or more dialogs**: one `.rc` file per dialog, named `<program>-<n>.rc`, beside the program.
- A program carries its dialog only when none of its other lines contains a dialog-loader keyword (CreateIndirect, WM_GetDialogItem, SetFont, SetText, AddString, AddColumn, SetGridVis, AddRow, SetItemText, SetTextColor, SetHeaderHeight, SetRowHeight, SetTitleVis, SetTextAlign); otherwise it uses the files.

Exits: continue = hold Ok; end = Cancel/Esc.

## A message that does not stop the program (toast)

1. The toast is a dialog whose FRAMEWIN row ends in 2: it stays on screen and the program runs on. *(AUDIT_R22)*
2. #100 closes it: with #100 = 1, the next MarcoDialog of the toast's file closes it. #100 survives power-cycles, and a leftover 1 stops the next toast from opening, so set #100 = 0 before opening one. *(AUDIT_R22, AUDIT_R23, AUDIT_R24)*
3. Close the toast before any other dialog and before the program ends (why: the firmware reading under "Not measured" below; not bench-measured).
4. Give a toast NO Ok/Cancel buttons. *(AUDIT_R33)* On a toast with buttons, Cancel looks like "stop" but closes only the toast: the next refresh opens it again and the program runs on. *(AUDIT_R22)*

The toast file ("Roughing"):
```
  { FRAMEWIN_CreateIndirect, "9", ID_FRAMEWIN_0, 2, 101, 1020, 360, 0, 100, 2 },
  { TEXT_CreateIndirect, "Text", ID_TEXT_0, 2, 28, 1024, 32, 0, 100, 0 },
    FRAMEWIN_SetFont(hItem, GUI_FONT_24B_ASCII);
    FRAMEWIN_SetText(hItem, "Message");
    hItem = WM_GetDialogItem(pMsg->hWin, ID_TEXT_0);
    TEXT_SetTextAlign(hItem, GUI_TA_LEFT | GUI_TA_VCENTER);
    TEXT_SetText(hItem, "Roughing");
    TEXT_SetFont(hItem, GUI_FONT_24B_ASCII);
```

The program lines around one toast:
```gcode
#100 = 1
MarcoDialog "/local/<program>-1.rc"
#100 = 0
MarcoDialog "/local/<program>-1.rc"
( ... the program runs on with the toast up ... )
#100 = 1
MarcoDialog "/local/<program>-1.rc"
#100 = 0
```

## Writing a dialog file

1. A type-9 dialog's held Ok writes no coordinate or setting: it only closes the dialog. *(AUDIT_R15 + state-file diff)*
2. The FRAMEWIN row's LAST field sets the mode: 1 = a normal blocking dialog (held Ok continues, Cancel ends the program); 2 = non-blocking (Ok ignored, the program keeps running; #100 = 1 then MarcoDialog closes it). *(AUDIT_R23 (1), AUDIT_R22 (2))*
3. A dialog whose frame row ends in 0 is modal: Cancel and Esc do not close it; only a held Ok does, and the program then runs on. *(AUDIT_R32)*
4. A dialog opened by MarcoDialog "<file>.rc" from a disk program closes on a HELD Ok (a tap does nothing) and the program continues. *(AUDIT_R1 (held Ok))*
5. Cancel discards the dialog's edits and ENDS the program; the keyboard Esc does the same in an Input Dialog (a .rc dialog, the Jogging-distance box) and ONLY there: a Message box (the boot "Go to home?" box) ignores Esc and cancels with PgUp. *(AUDIT_R2b (Cancel), AUDIT_R16 (Esc), bench keyboard sweep (Esc and PgUp per dialog kind))*
6. Cancel on a toast WITH buttons closes only the toast: the next MarcoDialog refresh opens it again, and the program runs on to its end. It does not stop the program, unlike Cancel on a normal dialog. *(AUDIT_R22)*
7. A TEXT line never wraps (one widget per line); only GUI_FONT_24B_ASCII is honoured on a TEXT widget; about seven 40-px rows fit a 360-px frame. *(AUDIT_R16)*
8. A backtick in dialog text draws a space; so does $42 (a message-table entry that is one space), ended by a TAB byte when a digit follows. *(AUDIT_R12, AUDIT_R15, AUDIT_R22)*
9. Dialog literal text: spaces, #, %, &, ; and ) are not drawn as written (stripped or read as commands); A-Z a-z 0-9 and ! * + - . / : = ? @ [ ] _ { | } ~ < > ' \ ( , draw as written. *(AUDIT_R8 (palette on the system disk))*
10. Dialog text commands: $n = message string n; ^n = the message string whose id is in #n; #n = the value of #n with 4 decimals; &n = the value of #n as an integer. Each takes every digit that follows. *(AUDIT_R13, AUDIT_R14)*
11. An EDIT widget: the CreateIndirect row's LAST field is the variable it reads and writes; EDIT_SetText carries the format #<min>max*width^k (decimal, sign + 4 places, width characters: #<-10000>10000*10 shows +0000.0000) or &<min>max*width^k (integer, width digits). EDITs added with their own ids work. *(AUDIT_R2, AUDIT_R21)*
12. An EDIT field is a digit wheel (TAB selects, X-/X+ move the digit, Y-/Y+ change it); a held Ok writes its value into the bound variable (single precision, about 7 digits). *(AUDIT_R2, AUDIT_R2b, AUDIT_R21)*
13. A RADIO widget: the row's second-to-last field is para = (spacing << 8) | item count (7683 = 30 px, 3 items), the LAST field the variable that receives the 0-based index; items set with RADIO_SetText(hItem, "<label>", <index>). *(AUDIT_R19)*
14. A RADIO writes the chosen 0-based index into its bound variable on a held Ok. *(AUDIT_R19)*
15. A RADIO draws as a single vertical list, one item per declared spacing pixel, regardless of how wide the widget rectangle is declared - there is no side-by-side layout and no per-item position, only a spacing and a count. It reads its initial selection from the bound variable on open and ALWAYS has something selected: an in-range value picks that item, an above-range value clamps to the LAST item, and a below-range value clamps to the FIRST item (unlike a DROPDOWN or LISTBOX, which show nothing selected below range). DOWN/UP step the highlighted item, a held Ok commits the 0-based index, Cancel/Esc discards it - the same convention every other widget on this firmware follows. *(t4042 C1 (a 10-item RADIO in a wide rectangle; a 3-item RADIO primed 0/1/9/-1; DOWN/DOWN/Ok and DOWN/Esc))*
16. Two RADIO widgets in one dialog, each with its own bound variable, are independent: TAB moves focus from one RADIO to the other as a whole, the arrows move between the items of the focused one, each keeps its own selection, and Ok writes each to its own variable. *(t4042 C1 (two 2-item RADIOs in one dialog, bound to separate variables))*
17. A RADIO's declared Para spacing (the top byte of `(spacing<<8)|count`) is a real, adjustable pixel gap, not a fixed constant - 60 instead of the usual 30 drew items twice as far apart, pixel-visible. But declaring more items than the available vertical room fits does NOT scroll, wrap into columns, or refuse: a 20-item RADIO in the standard frame silently drew only the first 9 and the remaining 11 never appeared anywhere, with no error, no scroll indicator, nothing to tell the operator more items exist. A generator placing a RADIO must compute how many items the declared height actually fits and must not rely on the firmware to catch an overflow. *(t4042 C1 radio follow-ups (Para=60<<8|3 for the spacing check; a 20-item RADIO in a 360-tall frame for the overflow check))*
18. With three or more separate RADIO widgets in one dialog, TAB cycles through them in the order they are DECLARED in the .rc's own widget array (not screen position, though the two usually match), and wraps back to the first after the last. Each keeps a fully independent selection - confirmed with three 2-item RADIOs, each stepped by its own DOWN while focused, all three writes landing correctly in their own separate bound variables with no cross-talk. *(t4042 C1 radio follow-ups (three RADIOs left/mid/right, own variables; TAB TAB TAB observed wrapping back to the first; DOWN on each through a held Ok))*
19. A LISTVIEW's own Enter key behaves differently from every other widget on this firmware: elsewhere, a TAP on Enter moves to the next widget (acts like TAB), and only a HELD Enter commits Ok. On a focused LISTVIEW, a plain tap toggles the CURRENT CELL into an edit mode instead - the cell switches to a zero-padded numeric display with a cursor, the dialog's own title bar turns from its active blue to a dark inactive grey, and the main screen's bottom button row (Start/Pause/Reset/.../Spindle) is replaced by a row of on-screen number boxes, an on-screen numeric keypad. A second Enter-tap exits edit mode cleanly, restoring the title bar and the bottom toolbar. A held Enter still produces Ok regardless of whether a LISTVIEW is focused or mid-edit, same as everywhere else. *(t4042 C1 part 3 (a 5-row editable LISTVIEW, Enter-tap entering and exiting cell-edit mode, confirmed on the physical panel by camera as well as Print Screen))*
20. Once a LISTVIEW cell is in edit mode (see the Enter-key fact), a USB DOWN key and a USB digit key did not change its value: the cell kept its zero-padded placeholder and the bound variable read back unchanged after a held Ok. Do not rely on editing LISTVIEW cells from a USB keyboard; how the panel keys or the other arrows edit a cell is not measured yet. *(t4042 C1 part 3 (DOWN and digit 7 both left a focused LISTVIEW cell's edit-mode display unchanged; #300-304 all read back 0 after a held Ok))*
21. A LISTVIEW row group's name spec binds a column to a variable per row through a `%` prefix: `E#%300` in a row group means row R's cell reads and writes `#(300+R)` - the same row-offset convention the vendor's own tool and WCS tables use (`probe-h.rc`'s H-table, `selcoord.rc`'s G54-G59 grid, `adjush.rc`). A cell without the `E` prefix is read-only; a bare `%` alone in a cell prints the row number itself, handy as a free row-label column with no variable needed. *(t4042 C1 part 3 (a 5-row, 2-column LISTVIEW: col 1 `%` showed 0-4, col 2 `E#%300` bound rows to #300-304) plus the vendor .rc grammar already on file (FIRMWARE-RE Sec4d))*
22. Declaring more LISTVIEW rows than the declared height fits does not behave like RADIO's silent drop (RADIO just never draws the overflow items). A 30-row LISTVIEW with a forced 18px row height packed noticeably more rows into the same vertical space than RADIO ever could at its fixed 30px spacing, suggesting row height is honestly adjustable; whether scrolling past the visible rows is possible by continuing to press DOWN was not confirmed in this session (only one DOWN was tried, which stayed within the visible rows). *(t4042 C1 part 3 (a 30-declared-row LISTVIEW, SetRowHeight(18), narrow columns))*
23. The full-picture erase (a focus transfer wiping an ENTIRE dialog picture, every chained picture at once) is specific to a focus transfer where BOTH the widget losing focus and the widget gaining focus are RADIO - not "any focus transfer," and not "a RADIO on either end." A decisive matrix, every scene laid out with no widget overlapping the picture and camera-confirmed at every key: TAB through 4 EDITs with a digit typed in each (closely matching a real CAM-builder export's own shape) left the picture fully intact through the whole walk; EDIT-to-RADIO and RADIO-to-EDIT (both directions) left it intact; RADIO-to-LISTVIEW and LISTVIEW-to-RADIO (both directions) left it intact. Only RADIO-to-RADIO erased it, in every test tried. A dialog that places its picture clear of every widget and uses EDIT fields (even alongside one RADIO, as long as the dialog never has TWO separate RADIOs the operator can TAB between) keeps its picture for the whole session. *(t4042 C1 decisive matrix (picture + 4 EDITs TAB-walked with digits each; picture + EDIT-RADIO-EDIT; picture + RADIO-declared-first then TAB to a LISTVIEW; all camera-confirmed, contrasted against RADIO-to-RADIO which erased every time))*
24. In a LISTVIEW cell's edit mode, LEFT visibly moves the edit cursor one position within the padded numeric display - a real, confirmed effect, the same cursor-move convention an EDIT widget's own field uses. UP showed no visible effect, and no digit typed after moving the cursor changed the cell's bound variable - the value read back unchanged after a held Ok. The panel's own physical keys (a separate input path from a USB keyboard) were not tried. *(t4042 C1 decisive matrix, LISTVIEW arrow-key check (UP, LEFT, a digit, RIGHT, a digit, each with its own camera look; #300-304 read back 0,0,0,0,0 after a held Ok))*
25. The vendor uses LISTVIEW for two genuinely different purposes, distinguished by whether its cells carry the `E` editable-cell prefix. probe-h.rc's own tool table has NO `E` prefix anywhere - it is a SELECTOR: the operator picks a row with DOWN/UP, and the row-selection variable (the widget's own Para field, #1824) is what the CALLING MACRO reads after Ok to do the real write itself, through indirect `#[]` addressing, once a probing cycle has run. selcoord.rc and adjush.rc's grids DO use the `E` prefix (`E#%0-#907` etc.) and ARE genuinely editable - their own callers are trivial two-line files with no post-Ok macro logic, confirming the dialog's own Ok-commit writes the edited cells straight to their bound variables, the same rule every other bound widget follows. A wizard that wants a real editable value table should follow the selcoord.rc/adjush.rc pattern, not probe-h.rc's. *(t4042 C1 decisive matrix (read probe-h.nc's own macro body: #1824 selects the row, #[1560+#1824] and #[764+#1824-1] are the indirect post-probe writes; selcoord.nc is two lines with no such logic))*
26. One file holds ONE dialog: two dialog blocks in one file draw one merged, broken dialog. *(AUDIT_R28)*
27. #100 is the dialog control variable: a normal dialog resets it to 0 while open, 1 closes a non-blocking dialog, and it survives power-cycles. Never keep data in #100. *(AUDIT_R22, AUDIT_R23, AUDIT_R24)*
28. The FRAMEWIN row's x, y, w, h ARE the window: screen-absolute pixels, drawn exactly as declared (2,101,1020,360 put the border at 2,101 to 1021,460), any size, not only full width. The controller's own files use five: 1024x506 at 0,44; 1024x503 at 0,47; 1020x360 at 2,101; 835x360 at 62,101; and a small 417x437 popup at 300,70; a hand-written 450x280 at 200,150 also opened exactly there. Child widgets do not move with the frame: each keeps its own absolute x, y, so a widget placed for a bigger frame falls outside a smaller one and is not drawn (Ok/Cancel placed for a 1020-wide frame vanished from a 450-wide one, and from a 150-tall one). The x, y in the file's GUI_CreateDialogBox call are ignored. *(t4039 (pixel-measured test dialog, vendor dialog captures, custom 200,150,450,280), t4042 part A)*
29. No frame size or position is refused and none crashed: 50x30, a frame running 176 px past the right edge and 100 px past the bottom, and one at x = -80, y = -40 all drew, clipped to the screen and to the frame. A 50x30 frame shows only a cut title chip. A frame at y = 0 draws its title bar over the top status bar. *(t4042 part A (8 hand-written frames))*
30. A frame taller than about 506 px (the largest ever confirmed working, the vendor's own biggest dialog) does not get clipped harmlessly at its own bottom edge or at the 600 px screen edge: its CONTENT simply stops being drawn once the running vertical position passes roughly 550 px from the top of the screen, whatever the frame declares. A 520-tall frame built with 10 field rows drew its title, its figure diagram and every field correctly, but its Ok/Cancel buttons - declared just past that point - never appeared at all: the real panel showed its own ordinary bottom toolbar there instead, with no trace of a button. The dialog still worked (a held Enter still closes it as Ok, independent of any visible button), but an operator has no visible way to confirm or cancel it. Keep a dialog's total content within the vendor's own proven frame size; do not assume a taller declared frame is simply clipped. *(t4043 bench proof (a real CAM-builder export, a 520-tall 10-field Surfacing dialog, pushed and run))*
31. The firmware draws a dialog with a white body, a 2 px black border, a pure-blue (#0000FF) title bar, black text and grey Ok/Cancel buttons, and the FRO label red; that is what Print Screen saves. A colour-invert parameter makes the panel show those colours inverted (a dark body, a yellow title bar, white text, a cyan FRO), and Print Screen ignores it: a capture always shows the un-inverted colours. The controller's own files name two fonts, GUI_FONT_24B_ASCII (title, buttons, TEXT, RADIO items) and GUI_FONT_13_ASCII (EDIT contents); the firmware knows only ten font names (the 8-, 10- and 13-px families: GUI_FONT_8_ASCII, 8_1, 10S_ASCII, 10S_1, 10_1, 13_ASCII, 13_1, 13B_ASCII, 13B_1, 13H_ASCII) and any other name, GUI_FONT_24B_ASCII included, draws in the controller's default font, which is what those captures show. TEXT_SetTextColor takes 0x00RRGGBB (in a capture 0x000000FF drew pure blue). *(t4039 (dialog bank captures; M6.rc colour check) against the 2026-10-07 R16 panel photo; the invert parameter: owner, 2026-11-06)*
32. Font size IS genuinely settable on TEXT/EDIT/RADIO/BUTTON (not ignored), and the look is chosen ONLY through the font name - not through its numeric prefix, which does not predict the rendered size the way a naive reading would suggest. Pixel-measured all 10 real font names plus GUI_FONT_24B_ASCII (not in the 10-name table) plus no SetFont call, one line each, cleanly spaced (an earlier cramped capture let the big fonts overlap and was retracted): exactly 4 real looks - LARGE NARROW (33px tall, ~20px/char advance): GUI_FONT_8_ASCII, GUI_FONT_8_1, GUI_FONT_10S_ASCII; MEDIUM REGULAR, not bold (24px, ~13px/char): GUI_FONT_10_1 only; MEDIUM BOLD (24px, ~14px/char, same height as medium regular but visibly bold): GUI_FONT_13_ASCII, GUI_FONT_13B_ASCII; SMALL (21px, ~11.5-11.9px/char): GUI_FONT_10S_1, GUI_FONT_13_1, GUI_FONT_13B_1, GUI_FONT_13H_ASCII, GUI_FONT_24B_ASCII, and a widget with NO SetFont call at all - all six render the SAME small look, GUI_FONT_24B_ASCII included (its own "invalid name" fallback and the "no SetFont" default are different mechanisms that happen to land on the identical rendered look, not different looks). Name -> look table: 8_ASCII/8_1/10S_ASCII -> large narrow; 10_1 -> medium regular; 13_ASCII/13B_ASCII -> medium bold; 10S_1/13_1/13B_1/13H_ASCII/24B_ASCII/(none) -> small. So GUI_FONT_13H_ASCII (or simply omitting SetFont) is the compact/dense choice; GUI_FONT_8_ASCII/10S_ASCII are the large, attention-getting ones despite their small-sounding names; GUI_FONT_13B_ASCII is the BOLD look at GUI_FONT_13_ASCII's own size, not a different size. The vendor's own dialogs set GUI_FONT_13_ASCII specifically on EDIT boxes (never 24B_ASCII, reserved for title/TEXT/RADIO/BUTTON) - that places EDIT text in the medium bold look, not the smallest one. *(t4042 font-size test (fonts-all-1/2.png: 12 lines, one real font name each plus no-SetFont, 40px row pitch after a first cramped attempt was retracted; cross-checked against fm-text/fm-radio/fm-button.png and three separate EDIT captures - macroMillRect.png, t4047-surface-current.png, fontsize-edit.png))*
33. The large-narrow look (GUI_FONT_8_ASCII, 8_1, 10S_ASCII) does not draw an underscore: the character still takes its full advance width (a visible gap where it should be) but no stroke appears. Every other look (medium regular, medium bold, small) draws the same underscore normally. Seen twice independently - a dialog TITLE set to that look, and a TEXT line in that look with an explicit colour - so it is the look itself, not one widget class. Avoid "_" in large-narrow-look text until this is explained; a "-" or a space reads the same and is known safe. *(t4048 font-matrix close-out (fm-title-large.png vs fm-title-medregular.png/fm-title-medbold.png; fm-colorfont.png))*
34. The controller colours one widget blue by itself. Two rules, which one fires depends on whether ANY TEXT widget in the dialog calls TEXT_SetTextColor: (1) BASELINE - a dialog with at least one EDIT and ZERO TEXT_SetTextColor calls forces the FIRST TEXT widget (creation order) blue by default, no colour call needed (confirmed 5/5, t4039). A dialog with a RADIO and no EDIT instead draws the RADIO's selected item blue and underlined; with neither, all text is black. (2) OVERRIDE - a dialog with AT LEAST ONE TEXT_SetTextColor call instead forces the FIRST widget that makes such a call blue, overriding its own requested colour - every later coloured TEXT keeps its own colour. Creation order decides, not the widget's numeric id (confirmed by swapping which one has the lower id - the swap changed nothing). A degenerate 1x1 "sacrificial" TEXT that calls SetTextColor first does NOT absorb the override; the next normal-sized coloured TEXT is still forced blue, so there is no known recipe yet for a wizard author to use an explicit TEXT colour safely. The generator that writes these dialogs never calls TEXT_SetTextColor at all today, so every dialog it builds is a BASELINE case - "Area X" rendering blue in a real Surfacing export is simply the first TEXT the generator creates (the anchored figure labels come first), not a separate mechanism. *(t4039 (comm-input, comm-choice, comm-prompt, comm-refusal, comm-toast, t4039-widget-test) for BASELINE; the OVERRIDE rule and the ID-vs-creation-order and sacrificial-TEXT tests: t4048 fm-colorfont.png + hl-a/b/c.png + sacrifice.png, 2026-11-06)*
35. An explicit TEXT_SetTextColor does NOT beat the controller's own automatic blue highlight (v41-dialog-default-highlight): a line declared magenta still drew blue in a dialog that also had an EDIT. Precisely (see v41-dialog-default-highlight): it is the FIRST TEXT widget in the dialog that calls TEXT_SetTextColor at all that loses this fight, not simply "the first text line" - in this test the first text line happened to be the first (and only) one coloured, so the two readings agree here. A later TEXT line's own declared colour is not affected and draws as declared, confirmed again by a 3-colour test (fm-colorfont.png) where the 2nd and 3rd coloured lines both drew their own colour correctly. *(t4039 title-bar follow-up T4 (a dialog with EDIT/RADIO/CHECKBOX/DROPDOWN/LISTBOX/BUTTON, first TEXT line coloured magenta); precision + re-confirmation: t4048, 2026-11-06)*
36. FRAMEWIN_SetTitleVis(hItem, 0) removes the title bar completely (no fill, no text), and the dialog's CLIENT AREA shifts up to fill the freed space: every other widget, declared at the same coordinates, lands about 38 px higher on screen than in the same dialog with its title bar left on. *(t4039 title-bar follow-up T2 (the same reference TEXT line and Ok/Cancel buttons compared with and without TitleVis))*
37. FRAMEWIN_SetTextColor does not recolour the title TEXT: it leaves the title bar's own fill colour unchanged (still the usual blue) and the title STRING DOES NOT DRAW AT ALL, even though FRAMEWIN_SetText still set it. There is no working way to change the title bar's own fill colour, or the colour of its text while keeping it visible, with a direct call. *(t4039 title-bar follow-up T1 (FRAMEWIN_SetTextColor 0x00FF0000, compared against a dialog with no colour call))*
38.
