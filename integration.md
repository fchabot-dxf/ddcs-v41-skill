## Keyboard

- A USB keyboard works: arrows jog, numpad Enter = Start (with NumLock ON; with NumLock OFF it turns the SPINDLE on: v41-kbd-numpad-enter), Pause = Pause, numpad 0 = Reset, Tab = file manager; Esc does nothing outside a dialog. *(owner keyboard test)*
- Print Screen saves the screen to /local/BMP<n>.bmp (1024x600, 16-bit). The counter restarts at BMP0 each boot and OVERWRITES the old BMP0.bmp: copy screenshots off before a power-cycle. *(owner Print Screen test)*
- F1-F7 are the seven soft keys under the screen, in order (Start, Pause, Reset, View, MpgGuide, Spindle, File): their meaning follows the page. F7 cycles the pages Main, File (the file manager), Param, Main. F4 = View, the I/O monitor (the first press after a page change is swallowed). *(bench keyboard sweep (F1-F7 and the I/O monitor))*
- F3 = Reset is a TOGGLE: the status box turns red RESET and F3 again clears it (Esc does not). It also stops a move under way. While the box is red RESET, Start is ignored. *(bench keyboard sweep (F3 twice) and the first bench-runner batch)*
- numpad / and F10 toggle the jog mode CONT / STEP (STEP opens an Input Dialog "Jogging distance"); F5 toggles the jog-mode highlight. *(bench keyboard sweep (numpad /, F10, F5))*
- Cancel depends on the dialog kind: Esc cancels an Input Dialog (the "Jogging distance" box; PgUp does not). PgUp, the panel's Z-up key, cancels a Message box such as the boot "Go to home?" (Esc, Tab, the arrows and the numpad do nothing to it). *(bench keyboard sweep (Jogging distance and the boot box))*
- The File page ignores the first TWO keys after it opens: Esc returned to the Main page only on the third press, 20 of 20 times (with or without another key first), while Tab into the File page registered 20 of 20. It is deterministic, not a random miss. Print Screen writes no screenshot on the File page. *(key_miss2 (20 cycles, the dongle, judged by webcam), 2026-10-29)*
- Ctrl+Alt+Del from a USB keyboard reboots the V4.1 without powering it down, and it recovers a FROZEN V4.1 (the nested-comment freeze): measured 2 reboots from READY and 2 of 2 freeze recoveries. The SMB port goes away about 3 s after the chord, the shares are back in 27-33 s, Print Screen answers in 35-95 s (the first attempts may fail while the boot finishes), and the boot "Go to home?" box is up (PgUp cancels it). The chord must be real: Ctrl and Alt held, then Delete. Measured only on the nested-comment freeze: the other freezes (#3000, a jump without Macro Mode, the 14-word M98, an in-place overwrite) were not retried with it. A reboot lost nothing the bench showed: the selected job and the DRO positions were the same afterwards (the bench is never homed, so a homed state is unobserved); it only brings back the boot "Go to home?" box. Use it before the power plug. *(a bench script chord / freeze (t3933))*
- Every dialog Ok on the V4.1 is a LONG press: on the panel the Z- (ENTER) key held about 1 s (a tap does nothing). A USB numpad-Enter (or Enter) HOLD is Ok on every dialog tested (MarcoDialog, Advanced Startup and the Simulation dialog), from the dongle and from a real keyboard; a TAP is not. How long, per dialog: a MarcoDialog took a 1.5 s hold 2 of 2 and a 1.8 s hold 4 of 5, the fifth HALTING the run (status RESET at the line after the dialog, cause not shown); Advanced Startup took 1.5 s and 2 s holds; the Simulation dialog took a 2 s hold 3 of 3 (1.5 s there is not measured). Hold about 1.5 s on a MarcoDialog, about 2 s on the Simulation dialog. The dongle and a real keyboard look identical to the controller (the same key-down, a repeat about 245 ms later, then one every 40 ms: evdev log, t3935). The hold must be a real one (the dongle's hold command, or a tap with a hold time): a plain tap does nothing. In a dialog PgDn is the RIGHT arrow (it moves the selection). A program that opens a dialog therefore needs a held Enter: an operator (Enter or the panel's ENTER), or a USB device that sends a real hold. *(the Simulation dialog, MarcoDialog and Advanced Startup walks (owner, dongle holds, real keyboard); evdev_log run 2; t3936; AUDIT_DLG_HOLD (a bench script, 7 runs); AUDIT_SEQ_P8001, AUDIT_SEQ_P8001_M0)*
- No USB key opens the Main page menu (Goto zero, Zero, Home, Probe, Advanced machining, Bias, Breakpoint, Coordinate origin, Centers, Simulation): the panel Shift key is a panel code from the motion device, not a USB event, so keyboard Shift, F8, numpad 7 and every other key do nothing there (Pr313 = 1 (Menu Mode) here; 0 = 2nd function). NumLock switches the keyboard between Mode 1 and Mode 2 on the Main page only. The menu items' dialogs can be opened by a program instead (v41-dialog-vendor-from-program). Measured again on 2026-10-24 with real holds: top-row digits, Esc, Tab, Enter, F2-F5, F7-F12, numpad / and numpad 5 and 6 (Mode 1 and Mode 2), and Ctrl, Shift and Alt with F2-F12, Esc, Home and Application, each tapped and held 2 s, opened no menu (a modifier is ignored on the Main page); numpad / and F10 held 1, 2 and 3 s only toggle CONT / STEP, so the vendor chart label Mode Shift on numpad / is the panel key picture, not a USB hold. No soft key on the Main, File, Edit or Param pages is a menu, Shift, Advanced Machining or Sequence key. *(the firmware key tables (keymap-firmware.json) and the bench: the owner's panel Shift, the dongle sweep, a bench script and the UI map (t3941))*
- A USB mouse does nothing on the V4.1: no pointer is drawn, and a click (or a held then released button) on 6 main-screen targets (the View and File... soft keys, the program-path box, the FRO field, a blank area, the far corner) and on Cancel of the boot "Go to home?" box changed no pixel. *(the t3885 native-pointer test (a USB mouse, no daemon, pixel diff))*
- A keyboard Start sent right after another key can be lost: Print Screen immediately before Space + numpad Enter (a 0.4 s gap) started nothing; with no key just before and a 1 s gap after Space, numpad Enter started the program (observed twice). *(the t3885 blit and cursor-daemon launches (dongle))*
- A USB HID keyboard emulated by an ESP32-S3 (TinyUSB device mode, which uses the S3's native USB port; a keyboard-only device, no USB serial interface) is accepted by the V4.1 as a keyboard, hot-plugged into its USB port, alongside a real keyboard (two keyboards work). It is not usable at once: the device reported itself enumerated about 2 min after the plug-in, and about 1 min after a controller reboot; whether that delay is the controller's or the device's is not measured. A build that added a USB serial interface to the keyboard (a composite device) was neither shown to work nor to fail. To the controller its keys are a real keyboard's (v41-kbd-ok-long-press), with the same conditions and hazards: Start is numpad Enter with NumLock ON only, and with NumLock OFF the same key starts the spindle (v41-kbd-numpad-enter); Backspace drives all three axes to work zero (v41-kbd-backspace); a dialog Ok is a held Enter, about 1.5 s on a MarcoDialog and about 2 s on the Simulation dialog (v41-kbd-ok-long-press). *(the bench keyboard device: hot-plug next to a real keyboard, its enumeration status, a Print Screen from it (t3623); its re-enumeration after a controller reboot)*

## Network shares and files

- Two SMB shares (guest): the work disk (cncdisk, programs) and the system disk (sysdisk); only ports 139/445 answer. *(port scan + share access)*
- Overwriting the selected program over the share BETWEEN runs and pressing Start again runs the NEW contents (resolved by name at Start). While it runs, never overwrite it in place: write a temp file and rename it over the program (v41-net-overwrite-rename). *(file-reload test (#230 = 1001/2002/3003))*
- An M47 (repeat from the first line) loop re-reads its file from disk every cycle. *(LOOP_TEST (3024 cycles))*
- There is no Modbus in the V4.1 firmware, and the serial port ignores arbitrary bytes. *(firmware string scan 2025-04-04, serial send sweep)*
- To replace a program while it runs, write a temp file and RENAME it over the program, never overwrite it in place: a rename left the running pass on the version it started with (2.6 KB and 515 KB files) and the new bytes ran at the next Start; an in-place overwrite of a 515 KB file while it ran froze the controller until a power cycle (one run; a 2.6 KB file survived it). *(AUDIT_OVERWRITE_LONG)*

## Variables and their files

- The system share's uservar file holds #100-#499 as 400 little-endian doubles (slot = #var - 100). *(uservar readback)*
- Variables reach uservar when a program starts and when it ends (also after an abnormal end), and also when it waits: a program paused at an M0 has the values written before it on disk, and an open dialog or toast rewrites the file every few seconds. In a running M47 loop the heartbeat variable stayed frozen on disk until the loop ended. A PC writing uservar changes nothing, before or during a run (v41-var-inbound-sealed). *(dispatcher heartbeat #246, inbound dwell test, AUDIT_UVAR_M0, AUDIT_UVAR_DLG, AUDIT_UVAR_TOAST)*
- Variables persist across M47 loops: nothing is cleared at the loop boundary, only assignment lines in the file change them. A counter line #N = #N + 1 survives (1, 2, 3, 4 over four loops) and a chain IF #N == 1 GOTO11 / IF #N == 2 GOTO12 / ... dispatches a different section each loop (Macro Mode on). A header line that assigns a literal (#M = 5) is run again every loop, so keep counters out of the header. uservar stays frozen while it loops except at the dwell flushes (v41-var-no-write-during-motion). *(AUDIT_M47FEED and AUDIT_M47EMPTY; t3943, t3945)*
- No run-time event reads the uservar FILE back into RAM. With A in RAM and a different value B written into the file by a PC, the program saw A after a program start (the file staged before the Start), a G04 dwell, an M0 plus a Start resume, the Pause key plus a Start resume, a program-opened dialog and its Ok hold, a Reset followed by a new Start, an M47 loop boundary and a Simulation run (2 of 2 each); only a reboot (the Ctrl+Alt+Del soft reboot) loaded the file: the program saw B (2 of 2). So a value reaches a RUNNING program only through the program FILE (v41-m47-reread), never through uservar, which is the way OUT (flushed at the start, at a dwell, an M0, a dialog and the end; a Simulation saves only at an M0). The B a PC wrote stays in the file after a dialog, M47 or Simulation run when the program does not reassign that variable. *(a bench script, 2 runs per event, and a bench script; t3942, t3944)*
- A program paused at an M0 already has its variables on disk: with #296 = 4321 before an M0 and #296 = 8765 after it, five reads of uservar during the pause (from 22 s after the Start) all gave 4321 with an unchanged file time, and 8765 appeared only after the run ended. The write happened AT the M0, not because of the read. Whether the file is written at each assignment or when the program stops at the M0 is not settled. Read a run's results AT an M0, not after the run ends: after the end the controller re-reads the file on disk and executes its assignments (the row on the after-run pass). A reader on a PC can miss this write: on the bench (Windows PC, the V4.1 share negotiating SMB1) an open()+read() of the uservar UNC path every 2-3 s kept returning the OLD copy, mtime included, for 40-55 s of pause (7 of 7 runs), while the same file read after a gap of 15 s or more showed the new value at once. A shutil.copy2 of the file to a local temp copy every 2 s and every 3 s saw the write at the first poll after the M0 (2 of 2 runs), so the reader matters: read uservar with a copy, or no more often than every 15 s. A community pipeline that polls every 3 s with shutil.copy2 over SMB1 reports detecting it, which agrees. *(AUDIT_UVAR_M0; AUDIT_M0CTL_A-D (open() vs shutil.copy2, 2-3 s and 15 s polls); t3939)*
- While a dialog or a toast is open, the V4.1 rewrites uservar continuously (the file time moved every 8-12 s between reads), with the values of that moment. A Reset during an M0 pause does not rewrite the file. *(AUDIT_UVAR_DLG, AUDIT_UVAR_EDIT, AUDIT_UVAR_TOAST, AUDIT_UVAR_RESET (t3900 steps 2-6))*
- Observed, not explained: 22 s into a 45 s G04 P45000 dwell, uservar already held the value written by the line AFTER the dwell. A value read from uservar during a run therefore does not show how far the program has got. *(AUDIT_UVAR_DWELL (t3900 step 4))*
- A WCS slot holds the frame's origin in MACHINE coordinates, and work = machine - slot: with G59 active, adding 7, 11 and 13 to #1542, #1543 and #1544 moved the work position #1506, #1507, #1508 by exactly -7, -11 and -13, the same before and after re-selecting G59 (no refresh needed). A write to a frame's slot takes effect for THAT frame whatever frame is active: a G59 slot write made with G54 active left the G54 work X unchanged. *(AUDIT_WCSSLOT (PASS 20/20))*
- G90 G92 X[#1500 - v] (v = the machine coordinate of the new origin) and the direct slot write #1542 = v leave the SAME work position (G59 active, X Y Z, difference 0 on all three), and #1500-#1502 read the current machine position at that point of the program. A specific frame's offset is the slot #[1512 + (frame - 1) * 6 + axis] (G54 X = #1512 ... G59 X = #1542; axis 0, 1, 2, 3 = X, Y, Z, A), written the same whatever frame is active. *(AUDIT_WCSEQ (PASS 13/13))*
- #790, #791 and #792 read 0, 0, 0 from a V4.1 program, the values parameters 790-792 hold in the system disk's setting file (0.0 each). The work position #1506-#1508 is not in that file: it is a live position variable. *(AUDIT_T3817_READ)*
- The `setting` file on the system disk is 12000 bytes: 1500 little-endian float64, slot 0 unused, and parameter #N is the 8 bytes at N x 8. The parameter names, units and enum labels are in the controller's own `custom` file on the same disk. The Param screen agreed with the file offsets in 113 of 113 readings (Pr001, Pr002-005, Pr007-010, Pr040-049 and more). Do not write the file from a program or a PC: it is the machine's configuration (what a write does is not measured). *(a bench script (t3954, 113 of 113 screen readings))*
- uservar is not written while a G1 move runs, even with a toast open (a 60 s move: no file change until the move ended); it is written at an M0, during a dwell or an open dialog, and at the end of the run. A PC polling uservar mid-move sees nothing new. Plain assignments after a G04 or a G1 can run AHEAD of it: in G04 P8000 / G91 / G1 X1 F300 / G90 / #210 = #210 + 1 the file already held the incremented #210 during the dwell, and a Reset then left that step counted as done (t3950: counts 1 / 1 / 1 instead of 1 / 2 / 1; the earlier dwell measurement says the same). A read of the machine position (#1500) waits for the motion (t3914, and t3950: #414 = #1500 before the increment made the Reset restart correctly), and so did a MarcoDialog toast refresh (t3914). The rule for a counter that must mean done: put a #1500 read after the last motion, before the assignment. *(AUDIT_LOOKAHEAD_TOAST; AUDIT_STEPSEQ_REDO / OVER and the _MA and _SY variants (t3950))*
- After a run ends, the controller makes a fast pass over the program file AS IT IS ON DISK (no dwells, no motion) and executes its variable assignments: a file replaced during the run left the NEW file's values in uservar about 22 s after the end, though that file never ran. Merely loading a file does not do it. So read a run's results at an M0, not after the end, when the file may have changed. This was measured after an ordinary program run; it was NOT seen after a firmware Sequence run (80 s of quiet uservar after the last part: v41-seq-machining). *(a bench script; AUDIT_SEQ_REAL (a bench script))*

## Inputs and outputs

- #1651-#1653 drive outputs 1-3 from a user program and read back: #1652 = 1 reads 1 and the output word #1650 reads 2; = 0 reads 0. #1650 = 7 is ignored (no error); #1652 = 0.5 reads 0 and -1 reads 1 (truncation). After #1651 = 1, M5 reads it back 0 (M5 clears OUT1). *(AUDIT_IO1)*
- Inputs read from a user program: with nothing wired, #1683 = 33554431 (bits 0-24 set) and #1684-#1699 all read 1; #1685 = 1 is ignored (read-only, no error). What a 1 means electrically is not measured. *(AUDIT_IO1)*

- ⛔ #1654-#1681 are output ports 4-31, NOT storage, although the vendor list calls them "Global variable area 2 (volatile)": a write switches an output bit. #1682, #1714 and #1715 drop a write. Never use any of them as scratch. *(firmware read: FIRMWARE-RE §11b, §11c; not a bench test)*
- #1684 + N - 1 reads input N (parameter port N = #(1683+N), on to #1713). It is the raw pin level: no active-level parameter is applied to it. *(firmware read: FIRMWARE-RE §11c; not a bench test)*
- External Start is Extended Function Key 1: its input port is Pr158, its active level Pr184, its function Pr250 (0 = Start, 1 = Pause). The key is decoded without the program reading the input word. *(firmware read: FIRMWARE-RE §11e; not a bench test)*
- Do not carry the Expert's input rule (#1520 + N - 1) here: on this controller #1518-#1521 are the G55 work offsets. *(named in the variable table, #1518-#1521; read/write behaviour not bench-measured)*
