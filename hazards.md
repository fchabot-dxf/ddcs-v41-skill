# DDCS V4.1 — hazards

> Every measured statement names the bench test that measured it (see evidence.md).


- **Macro Mode**: a jump or loop without #122 = Enable halts or freezes the controller.
- **#100 is reserved**: #100 is the DDCS V4.1's dialog control variable: any dialog resets it to 0. Never store anything in it.
- **#101 is reserved**: #101-#148 are the DDCS V4.1's own dialog memory (the operator's remembered tool-change and probe defaults). Never store anything in it.
- **#102 is reserved**: #101-#148 are the DDCS V4.1's own dialog memory (M6.rc binds #102-#105). Never store anything in it.
- **#103 is reserved**: #101-#148 are the DDCS V4.1's own dialog memory (M6.rc binds #102-#105). Never store anything in it.
- **#104 is reserved**: #101-#148 are the DDCS V4.1's own dialog memory (M6.rc binds #102-#105). Never store anything in it.

## Measured on this controller

- In standard mode (#122 = Disable) a program with a jump can FREEZE the controller with the panel showing the spindle on; a power-cycle is needed. *(AUDIT_S5c_rerun (#122=0))*
- ⛔ M98 P<n> runs the VENDOR subprogram when the vendor library has that number, not the O<n> in your own file. With its own O9103 in the file (it sets a marker), M98 P9103 left the marker at 0 and ran the vendor's G103 ellipse (slib-g.nc), which with no step never ended (1 run with the marker, 5 more hangs on P9102 and P9103). slib-g.nc holds O9100, O9102 and O9103: look a number up in the controller's slib files before you use it. *(ALIAS_SHADOW_9103, ALIAS_FLOW_M99 (alias matrix))*
- ⛔ A program that never ends shows READY. In every hang measured (the vendor ellipse above), the status box read READY while the mode box to its left read AUTO and the run timer counted, once for over an hour, and every Start was ignored; two Resets ended it (CONT, RESET, then READY). CONT in the mode box means no program is running, with one exception: a Sequence machining part paused at an M0 or by the Pause key reads CONT and READY too (v41-seq-stop-actions). *(ALIAS_FLOW, ALIAS_FLOW_M99, ALIAS_SHADOW_9103 (alias matrix))*
- ⛔ M98 P9001 X5 to an O9001 placed AFTER M30 did not run the subprogram: no error, the program just went on. And reaching an O line in the main flow ENDS the program there, silently. Put a subprogram BEFORE M30 and jump over it (syntax.md, the measured recipe). *(AUDIT_HW1, AUDIT_HW2)*
- ⛔ Writing #3000 = 1 (text) FROZE the controller (Reset lit, no message, power-cycle needed), with Macro Mode on. Never write any variable from #2000 up on this controller: not the Expert's #2042 beep, #2070 number entry or #3000. *(AUDIT_MSG1)*
- ⛔ A program with a bad line is NOT inert, and what has run when it stops is uneven. No bad line was refused at load: the controller reads ahead of the line it executes and stops the run (RESET) when the parser reaches the bad line, measured from the line just before it to 49 lines before it. Some variable writes before the bad line had run (a step counter read 10 of 10 in one run, 5 in another), but the MOVES within that reach did not: ten G1 steps, and a G1 X4 with a position read and 15 lines after it, left the axis where it was (4 runs). A position read in that window stored 6.5 while the axis stood at 3. *(S6e, ALIAS_SPACE_MOVES, ALIAS_SPACE_MOVES_SYNC, ALIAS_SPACE_MOVES_FAR, ALIAS_NUM_COORD (alias matrix))*
- A comment holding a ")" before its end stopped the program with "Unrecognized file format: L1" (first read as a load refusal; re-run on 2026-10-29 after twelve counted lines it is a mid-run stop: those lines ran, the error named the NEXT line, and the controller did not freeze): the parser ends a comment at the first ")", and the text after it is not valid code ("Unrecognized file format: L1[<leftover>"); a leftover that happens to be valid code can pass (MOD_ZERO, 2026-10-15): see v41-comment-trailing-code. *(AUDIT_R30 (first attempt), ALIAS_CMT_NESTED (alias matrix))*
- #100 is the dialog control variable: a normal dialog resets it to 0 while open, 1 closes a non-blocking dialog, and it survives power-cycles. Never keep data in #100. *(AUDIT_R22, AUDIT_R23, AUDIT_R24)*
- Confirmed again on the bench: a comment with nested parentheses, ( ... (vendor) ... ) on line 1, stopped the program on line 1 ("Unrecognized file format: L1"), so nothing ran: the text after the first ")" is not valid code. A nested pair whose leftover happens to be valid code can pass (MOD_ZERO the same day); see v41-comment-trailing-code. *(a comment holding (vendor) on line 1)*
- ⛔ The V4.1 reads slib-m.nc ONLY AT BOOT: a merged slib-m.nc copied onto the system disk while it ran did nothing (M12 and M98 P10012 silently did nothing, no error); after a power cycle both ran. A sent M-code needs a controller restart. The merged file itself was accepted: the vendor bytes kept, all CRLF, an appended O-block with an em-dash in its header. *(a merged slib-m.nc with an O10012 block, M12 and M98 P10012, before and after a power cycle)*
- An M30 does not end a run that is looping on M47: the run keeps cycling (stop it with Reset). That was measured on a file swapped mid-run to one ending in M30; an M30 that the loop file ITSELF reaches by a GOTO before its M47 line did end the loop cleanly, 2 of 2 (v41-m47-end), so reach the M30 from inside the loop file. An M02 in that place did NOT stop the loop at once: it spun on and stopped by itself about 11 s in (v41-m47-end); use M30. *(the M47 swap trials (ending in M30); AUDIT_M47FEED (t3943))*
- ⛔ Never write uservar from a PC, an ESP or any other device, not even between runs. No run-time event reads the file back (a program start, M0, Pause, a dialog, Reset, M47, Simulation: the program keeps its RAM value); only a reboot does (v41-var-inbound-sealed). The controller overwrites the file at its next save. To give a running program a value, put it in the PROGRAM FILE (replace the file by rename: v41-recipe-feed-running-program); read uservar only after a save point (an M0, a dialog, the end of the run). *(a bench script, 2 runs per event, and a bench script (t3944))*
- The homed mark is not settable by a variable: #1806 is the vendor home macro's flag, not "homed" (a program writing #1806 = 1 ran and X kept its not-homed mark; #1806 = 1 with G91 G28 X0 started a REAL homing search). Homed means a G28 that FINDS its switch. Do not carry the Expert's homed flags #1515-#1518: on the V4.1 they are work offsets. *(the home flag test (a #1806 write, then G91 G28 X0))*
- ⛔ A subprogram must never read a letter its caller did not pass: the V4.1 does not clear the local slots of a sub between calls, and they hold GARBAGE, not 0. On an M98 call the words land X #1, Y #2, Z #3, A #4, B #5, C #6 and I #7 (#0 is unused); a call with no words left #0-#33 summing 30307, and an I5-only call left #0 = 2.4e-306, #8 = 5.3e-315 and #33 = 14.96. A sub that reads a local the caller left out reads a random number. *(BIBLE_M98_I_MAP, BIBLE_M98_LOCALS, BIBLE_M98_AXES)*
- ⛔ #490-#495 belong to the firmware, not to a program: it writes the MACHINE POSITION there for power-off recovery (the vendor safez.nc itself assigns #490 = #1500 up to #495 = #1505, X Y Z A B C). Probe slots #490-#492 read 3388.75, -754.59 and -56.12 after a run, the position of the machine, and #493-#495 read 0. They sit inside the persistent #100-#499 band, so they look free: never store data in #490-#499. *(BIBLE_M98_POS_H and BIBLE_M98_POS_D (slots #490-#495), the vendor safez.nc)*
- ⛔ A GOTO, or an IF whose jump is TAKEN, to a label the file does not define ENDS THE PROGRAM SILENTLY at the jump (Macro Mode): no error, no message, the status box reads READY and the run looks finished. The lines before the jump ran, the lines after it did not. A jump that is not taken does nothing, and a label defined twice is accepted: a jump goes to its FIRST definition. Check every jump label against the file before sending it. *(BIBLE_GOTO_MISSING, BIBLE_IF_MISSING_TAKEN, BIBLE_IF_MISSING_NOTTAKEN, BIBLE_GOTO_DUP)*
- ⛔ A variable set in the CALLER does not reach a subprogram: #1 = 505 (or 342, 585, 586, 587) before M98 P8001 still opened the PLAIN "Advanced Startup" dialog, all five times, so the vendor O8001 never saw its #1. ⛔ And a variable that is NOT passed is STALE, not zero: a bare M98 P8001 after a call that passed X587 opened "Load breakpoint: Sequence" (Line No. 12), because the subprogram's #1 kept the stale #1 of 587 (locals are not cleared between calls; v41-m98-local-garbage). M98 P8001 X0 opened the plain "Advanced Startup". Always pass the word. The words of the M98 call DO land in the sub: M98 P8001 X505 does reach it (X #1, Y #2, ...: v41-m98-letter-slots) and opens the Array variant. *(AUDIT_PREFILL497 (bare call, stale #1), AUDIT_PREFILL497_X0, AUDIT_MENU_ADVSTART_ARRAY, _SEQ and AUDIT_MENU_BREAK_SINGLE, _ARRAY, _SEQ (caller variable: plain dialog) against AUDIT_MENU_ARG_* (argument form: each its own dialog))*
- ⛔ A program left paused at an M0 and cleared with Reset (the box back to READY) keeps its run: the NEXT Start resumed it and ran the OLD program's remaining lines to its M30, instead of the new file. End a program with M30, never leave it at an M0; after a Reset at an M0, check which program a Start will run. *(AUDIT_SEQ_ENTRY and AUDIT_SEQ_RUN (t3925))*
- ⛔ Pause LIFTS Z on its own by Pr904 (5 mm here, relative: Abs Z 0 -> 5.000, real motion), run by the vendor pause.nc; F1 Start resumes and Z returns. A pause near a clamp, a hold-down or the workpiece edge lifts the tool into it: check Pr904 before pausing (and Pr903, which the vendor pause.nc reads to park instead: un-v41-pause-park). *(AUDIT_ADV_LONG (Pause by hand) and the vendor pause.nc)*
- ⛔ The vendor owns #490-#499: never write them, with ONE measured exception. #490-#495 hold the machine position (v41-var-490-position), #496 counts the parts of a Sequence run (0, 1, 2: v41-seq-machining), #497 is the Advanced Startup "Specified line", and the dialogs a program opens overwrite #497 and #498. The exception: #497 = N before M98 P8001 X0 pre-fills the Specified line (#497 = 12 showed 00000012; #497 = 1 before M98 P8001 X342 showed 00000001); write #497 only for that. What #101-#148 and #499 do is read in the vendor files, not run (un-v41-vendor-dialog-memory). *(BIBLE_M98_POS_H and BIBLE_M98_POS_D, AUDIT_SEQ_REAL (t3940), AUDIT_PREFILL497_X0, AUDIT_SEQ_P8001 and AUDIT_SEQ_P8001_M0)*
- The status box reads READY while a program is paused at an M0, not only when it has ended: READY does not tell a paused program from a finished one. *(AUDIT_UVAR_M0)*
- ⛔ A G92 shift is not temporary: a +5 G92 shift in the G59 X slot was still there for the next program, after the program that made it ended with M30 and after a Reset. Undo it yourself: writing the saved slot value back into #1542 restored the slot exactly. Whether it survives a power cycle is not measured. *(AUDIT_G92WCS_P1_LEAVE, AUDIT_G92WCS_P2_READ (baseline read first), AUDIT_G92WCS_P3_RESTORE)*
- ⛔ A G53 move is REFUSED while the axes are not homed: G0 G53 Z#1402 stopped the program at its own line with "HOME operation not performed:L29[G0 G53 Z#1402]" on the status line and the status box RESET; no axis moved, the lines before it had run and nothing after it ran. A program that retracts or parks in machine coordinates needs a homed machine (homed means a G28 that found its switch: v41-var-homed-mark). *(AUDIT_FUSIONTAIL (verify-motion, t3873b))*
- Check the controller's safe-height and park parameters before a program moves to them: on the bench (apparently the factory state) #1402 (Pr902, the safe height) = 5, #1302 = 10, #1300 = 30, #1301 = -30, #1400 (Z returns to the safe height) = 0, #1403 (the park flag pause.nc reads) = 0 and #1404 = 5 (the relative lift pause.nc uses when #1403 is not 1). Z is up positive (a pause lifted machine Z from -56.12 to -51.12), so a machine Z of +5 or +10 is above the machine's zero. Where a G53 move to these values lands is not measured: it needs a homed machine. *(AUDIT_FUSIONTAIL (the parameter snapshot before the G53 refusal))*
- ⛔ A MarcoDialog that showed no buttons was a modal that nothing but a POWER CYCLE cleared: the clock kept ticking and Esc was ignored (observed once). Give every blocking dialog an Ok and a Cancel; the measured buttonless exception is the toast (frame row ending in 2), which #100 = 1 closes (v41-dialog-buttonless). *(the t3885 evdev-probe launcher (a selcoord.rc MarcoDialog, observed once))*
- ⛔ An open buttonless toast swallows the USB Reset: with a toast up (a program calling MarcoDialog on a frame whose last field is 2), F3 and numpad 0 sent during a step were ignored and the run went on to its end. Esc closes the toast only (the run continues), and THEN the Reset works (a red RESET box; a second Reset tap clears it before the next Start). The toast is a dialog and it captures the USB keys. Whether the panel Reset button is swallowed as well is not measured (it needs a person at the machine); an E-stop was not tried. *(a bench script: Reset in step 2 with the toast open (ignored), then Esc plus Reset (worked); t3950)*
- ⛔ Two sequential WHILE [cond] DO1 ... END1 blocks that reuse the SAME DO id hang the program: each loop runs its exact count, then the run never reaches the code after them and does not end by itself (stop it with Reset). No M98 and no motion are needed. Measured with an end marker (#473 = 1) just before M30: loops of 3 and 3 iterations gave counts 3 and 3 and #473 = 0; both loops false gave 0 and 0 and #473 = 0; loops of 4 and 2 with G-code moves before, between and after gave 4 and 2, #473 = 0 and a run still going after 88 s. The second symptom is worse: when each loop is followed by an M98 call of the same sub, the second M98 returns to the FIRST call site and the run runs away: 6 sub runs (cut by a guard), the line after the first call executed 5 times, the line after the second call 0 times; on the real program #150 passed 2376 and it went on for more than 14 minutes until a Reset. It happened for every loop value tried (41, 40, 5, both loops false). A distinct id per loop (the second block on DO2 and END2) or IF and GOTO loops instead of WHILE removed both symptoms: the end marker was reached (#473 = 1) and the real program ran to its M30 (2 of 2). Fine on their own: one WHILE block, a sub called twice from the main flow, a nested sub call, one skipped WHILE then one call, and an IF and GOTO dispatcher. [HYPOTHESIS, not tested] the interpreter keeps one loop record per DO id, and a reused id leaves a record that the next END1 or M99 goes back to. [TO TEST] whether DO2 and DO3 blocks reused the same way fail too, and whether two WHILE blocks on one id fail when the first is nested inside another loop. *(AUDIT_WHILE_SEQ A B C and A_DO2; AUDIT_DISPATCH_REPLICA B-G, AUDIT_M98_TWICE, AUDIT_M98_NESTED, AUDIT_WHILE_SKIP_M99, AUDIT_SERIAL_JOB_NOG53 and _DO2; t3964, t3968)*
- ⛔ A program with a comment that nests a parenthesis stopped and left the controller NOT ANSWERING: no message, no Print Screen, a screen that never repaints; Esc, PgUp and the Reset key did not clear it, only a power cycle did (three times, 2026-10-23; earlier stops, 2026-10-08 and 2026-10-15, showed a message instead, and the 2026-10-29 re-run after twelve counted lines stopped mid-run, named the next line and did not freeze: why it differs is not known); on 2026-10-23 Ctrl+Alt+Del from a USB keyboard also recovered it, 2 of 2 (v41-kbd-ctrl-alt-del). A comment ends at its first ")", so never put "(" or ")" inside a comment. *(a bench script)*
- ⛔ An inline IF .. THEN does not refuse the file at load: the program starts and stops mid-way with RESET. *(AUDIT_V8_then, ALIAS_OLD_THEN (alias matrix))*
- ⛔ A line with a leading space does not refuse the file at load: the program starts and stops part-way ("Unrecognized file format: L<n>[...]" and RESET) when the parser reaches that line, before the run gets there (7 lines before it in one run), with no warning at Start. Start every line at column 0. *(AUDIT_LABEL_COL0, AUDIT_LABEL_SP1, AUDIT_LABEL_SP1_FAR)*
- ⛔ <>, NOT[], &&, ||, SQR[], a one-argument ATAN, ATAN[y]/[x], POW[], **, % (as an operator), GO TO, a / block delete line, a leading + on a number, an exponent (1e2) and a decimal comma (0,5) do not refuse the file at load: the program starts and stops mid-way with RESET. *(ALIAS_CMP_WORDS, ALIAS_LOGIC, ALIAS_MATH, ALIAS_FLOW, ALIAS_BLOCKDEL, ALIAS_NUM_COORD, ALIAS_NUM_VALUE, ALIAS_EXP_UPPER (alias matrix))*
- ⛔ ! is not NOT: #v = !0 gave 0 with no error, and the program went on with that value. *(ALIAS_LOGIC (alias matrix))*
- ⛔ 7 MOD 3 stops the run (RESET) when the read-ahead reaches it, up to about 18 lines before its own line: use MOD[a, b]. *(the alias gaps, 2026-10-30)*
- ⛔ G04 P3.0 is 3 ms, not 3 s, with no error: write G04 P3000 for 3 seconds. *(the alias gaps, 2026-10-30)*
- M6 in a program does NOTHING while Pr905 "Tool change command M6 back to reference point 1 pause" is No (the factory value): no pause, no dialog, no move, and the current tool is not set; the program runs on. With Pr905 = Yes, M6 runs the vendor tool change (O10006 in slib-m.nc), whose first move is G53 to the tool-change point, so an unhomed machine stops there ("HOME operation not performed"). *(the M6 test, 2026-10-30 (Pr905 No, then Yes; restored and byte-compared))*
- ⚠ An exact == on a computed decimal can miss with no error: 0.3 - 0.2 == 0.1 was false. Compare with a tolerance. *(ALIAS_DEC_AXES (alias matrix))*
- ⛔ M099 at the end of a subprogram does not return: the program ends there silently, and the lines after the M98 call never run. Write M99. *(ALIAS_FLOW_M099, ALIAS_FLOW_M099_ARG, ALIAS_FLOW_M099_FREE, ALIAS_FLOW_M99_FREE, ALIAS_DEC_ARGS (alias matrix))*
- ⛔ An unknown character in an expression is silently dropped, with no error: 2 + ^3 evaluated to 5. A formula written with ^ (a power in other dialects) computes something else here. *(AUDIT_MATH1)*
- ⛔ M5 clears output 1: after #1651 = 1, an M5 reads it back 0 (M5 clears OUT1). Do not put a device that must stay on through a spindle stop on output 1. *(AUDIT_IO1)*
- ⛔ AND, OR and XOR do not refuse the file at load: the program starts and stops mid-way with RESET. *(AUDIT_REMATH_AND, AUDIT_REMATH_OR, AUDIT_REMATH_XOR, ALIAS_OLD_AND (alias matrix))*
- Param page edits are saved ONLY when the page is left with Main... (F7); Esc or Logout discards them without a word. *(#324 change, settings file watched)*
- ⛔ A comment that is never closed is NOT refused: it silently swallows every following line up to the next ")" in the file, or to the end of the file with M30 included, so the code on those lines (a retract, a spindle stop, the M30) does not run. Close every comment on the line that opens it. *(AUDIT COMMENT CASE: unclosed, unclosed_closes_later)*
- ⛔ Text after the ")" of a comment on the same line RUNS when it is valid code: G0 X0 (note) X5 moved to X5, and (note) G0 X0 ran its G0. Nothing but the end of the line is safe after a ")". *(AUDIT COMMENT CASE: post_x, post_g; BIBLE_SQRT_VALUE; ALIAS_CMT_TRAIL_BAD (alias matrix))*
- numpad Enter = Start only with NumLock ON. With NumLock OFF it turns the SPINDLE ON (M3, S 24000) and does NOT start the program. Plain Enter does not start a program. A keyboard or a script must know the NumLock state before it sends Start. *(bench keyboard sweep, NumLock off and on (twice))*
- ⛔ Backspace = GO TO ZERO: one tap drove all three axes to work zero at about F5000 (the status bar read GOTOZERO... / BUSY). Esc does not stop it; F3 (Reset) does. On a live machine a stray Backspace is an unconfirmed rapid to X0 Y0 Z0. *(bench keyboard sweep; F3 half a second after Backspace)*
- ⛔ F6 = SPINDLE on/off: the first press sets M3 and S 24000, the second sets M5. On a real machine a stray F6 STARTS THE SPINDLE. *(bench keyboard sweep (F6 twice))*
- ⛔ The numpad is a jog pad (CONT mode, one tap each, pairs returned the readout exactly): 6 / 4 = X+ / X-, 8 / 2 = Y+ / Y-, 9 / 3 = Z+ / Z-; the arrows jog X and Y, PgUp / PgDn jog Z. On a real machine every numpad digit but 5 moves an axis. *(bench keyboard sweep (jog pairs))*
- ⛔ On the Main page a USB keyboard HOLD does what a tap does not for some keys: numpad * held about 2 s = ZERO Z and numpad 5 held about 2 s = ZERO XY. It silently rewrites the work zero (Abs Z or Abs X and Y go to 0.000 at the current position, the G54 offset changes); a tap does nothing visible. The vendor keyboard chart says to hold these keys over 3 seconds (it is for software 2022-11-02 or earlier); on 2025-04-04 about 2 s was enough, because the hold is the first kernel key repeat, not a timer. In Mode 2 (NumLock) the chart names numpad * = Zero A, 7 = Home and 3 = Fix Probe the same way (not tried here). Numpad - and + held also ramp the jog speed JSR by 5 % per repeat (100 % down to 0 % and 0 up to 110 % in 2 s: JSR is not capped at 100 %). So a program, a script or a held key on a USB keyboard can change the work zero or the speeds without a dialog. Put back by writing the work position variables (#1506 X, #1507 Y, #1508 Z, as the vendor zeroxy.nc and zeroz.nc do) to the old values, and the JSR with + and - taps. *(a bench script: numpad * and 5 holds, AUDIT_WCS_RESTORE put the zero back; t3941)*
- ⛔ Keep an M98 call to a few words: a call with fourteen words (I J K Q R U V W F S T H D E) stopped the run and the V4.1 then ignored every key until a power cycle; any two of U, V, W on one call stop the run mid-way, after some writes before it may have run. *(BIBLE_M98_AXES, BIBLE_M98_I_MAP, BIBLE_M98_POS_J to _T and _U _V _W _E _H _D, BIBLE_M98_MAP_ALL, BIBLE_M98_LETTERS, BIBLE_M98_COMBO_UV _UW _VW _UVW)*
- ⛔ Deleting template.txt does not clear the Sequence machining table: the page reads a converted copy named "template" on the system disk, and after template.txt was deleted it still showed the old rows (the part origins a Sequence run adds to the work coordinate). Check the table on the page before every Sequence run. *(template.txt on the bench (Sequence machining page) and AUDIT_MENU_TEMPLATE_RC)*
- ⛔ A Sequence machining part with NO motion in it resets the run: about 5 s after the page Ok the status went RESET with no message and no line of the part ran (2 of 2; the page showed the X, Y and Z range as [100000,-100000]). The same part with a 0.1 mm move and back added ran all its parts (1 of 1). A part that only writes variables or dwells needs at least one move to run under Sequence machining. *(a bench script (R1-R2c, S1-S5, S4a/b), real panel-menu Sequence runs, 2026-10-29)*
- ⛔ Inside a Sequence machining part, Start after a pause RE-RUNS the part from its first line; it never resumes. After an M0, every Start re-ran the part from the top (8 of 8), the code after the M0 never ran and the sequence never reached the next part, so an M0 for a tool change makes the sequence loop on that part. After the Pause key and Start, the part also ran from the top again, then the next parts ran (1 run). On a real machine everything before the pause is cut again. Do not put an M0 in a program run by Sequence machining. *(a bench script (R1-R2c, S1-S5, S4a/b), real panel-menu Sequence runs, 2026-10-29)*
- ⛔ A division by zero does not stop the program: 1 / 0 returns 0 and MOD[7, 0] returns 0 with no error, and SQRT of a negative number returns NaN (every comparison against it, == 0, > 0 and < 0, is false). The program goes on with that value: test a divisor or a root argument yourself before the line. *(BIBLE_DIV_ZERO, BIBLE_MOD_ZERO, BIBLE_SQRT_NEG, BIBLE_SQRT_VALUE)*
- ⛔ Never overwrite a RUNNING program in place over the share: an in-place overwrite of a 515 KB file while it ran froze the controller until a power cycle (one run; a 2.6 KB file survived it). Write a temp file and RENAME it over the program: the running pass keeps the version it started with, and the new bytes run at the next Start. *(AUDIT_OVERWRITE_LONG)*
- ⛔ A plain assignment after a G04 or a G1 can run AHEAD of it: a step counter incremented after the motion was already on disk during the dwell, and a Reset there left the step counted as done (counts 1 / 1 / 1 instead of 1 / 2 / 1). For a counter that must mean done, put a read of the machine position (#1500) after the last motion, before the assignment. *(AUDIT_LOOKAHEAD_TOAST; AUDIT_STEPSEQ_REDO / OVER and the _MA and _SY variants (t3950))*
- ⛔ After a run ends, the controller makes a fast pass over the program file AS IT IS ON DISK and executes its variable assignments: a file replaced during the run left that file's values in uservar, though it never ran. Read a run's results at an M0, never after the end when the file may have changed. *(a bench script; AUDIT_SEQ_REAL (a bench script))*

## Not measured, but a machine-safety rule

- A partial write to uservar can truncate the file and lose #100-#499 (community report, one user, 2026-10-29; not measured here). Restore uservar from a backup before running if a write may have failed. *(a community report, 2026-10-29; see v41-hazard-uservar-write)*
- The after-run pass executes a file's variable assignments again (v41-var-after-run-reread). Whether that includes assignments that switch an output (#1651-#1653) or write a work offset (#1512-#1551), and whether a pass also runs at the Start, is not measured. Never leave an output or offset write in a program file that may be replaced or changed after its run. *(controllers/v4.1/FINDINGS.md (AFTER A RUN ENDS THE V4.1 RE-READS THE FILE ON DISK; [TO TEST] the pass at the Start))*
- What a write to the setting file on the system disk does is not measured (it holds the machine's configuration: parameter #N at byte N x 8, v41-setting-file-layout). Never write it from a PC or a program; read it only. *(the file was only read (t3954); no write was made)*
- What Ok does on the controller's own dialogs opened by a program (selcoord.rc, adjush.rc, center.rc, array.rc, template.rc, the Simulation dialog of M98 P8003) is not measured: the probes closed them with Esc.
